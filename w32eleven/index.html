W32Eleven

Run 64-bit Windows 11 on a 32-bit PC. W32Eleven is an x86-64 PC emulator that runs directly on the hardware of 32-bit x86 machines, boots from a patched Windows install DVD or USB stick, and translates Windows' 64-bit code into 32-bit code with its own JIT.

Source on GitHub Quick start

Overview

Windows 11 only exists for 64-bit CPUs. W32Eleven makes it run on CPUs that can't execute 64-bit code at all (i386 or later with an x87 FPU; no SSE and no 64-bit mode needed) by emulating a complete x86-64 PC. Windows is not modified: it sees an ordinary 64-bit PC with a BIOS, a VGA card, IDE disks, ACPI and two CPUs.

32-bit PC (for example a Core Duo or an Atom N450) └─ GRUB (from the patched DVD / USB stick, or from the hard disk after installing) └─ W32Eleven, bare metal, i386 + x87 only └─ emulated x86-64 PC: SeaBIOS, VGA, IDE, ACPI, APIC, 2 CPUs └─ Windows 11 (unmodified)

There is no Linux or other operating system underneath. The emulator is a small Multiboot kernel that GRUB loads directly, with its own drivers for disks, display and input.

Requirements

To build and patch (a Linux PC)

  • GCC with 32-bit support (lib32 glibc for the 32-bit test harness), GNU ld, NASM, Python 3, make
  • GRUB with i386-pc support (grub-mkstandalone) and xorriso, for the patch tool
  • SeaBIOS and the VGA BIOS (the patch tool uses QEMU's copies in /usr/share/qemu/ by default)
  • qemu-system-i386 for testing (KVM recommended)
  • A Windows 11 x64 ISO, downloaded from Microsoft

To run Windows (the 32-bit PC)

  • A BIOS PC, or a UEFI PC with CSM / legacy boot enabled
  • An x86 CPU, i386 or later, with an x87 FPU
  • As much RAM as possible. Windows gets roughly what the PC can address below 4 GB minus the emulator's share (about 2.8 GB on a 3 GB machine).
  • A hard disk of at least 64 GB for Windows 11
  • A DVD drive, or a USB port the BIOS can boot from

Quick start

1. Build

git clone https://github.com/Banaxi-Tech/W32Eleven.git
cd W32Eleven
make            # build/emulator.elf (bare metal), build/hosted, build/hosted32
make test       # bare-metal self-tests on a QEMU 486

2. Patch your Windows ISO

python3 tools/w32-patch-iso.py Win11_x64.iso Win11_w32eleven.iso

This copies the ISO and appends the emulator, SeaBIOS, the VGA BIOS, two small answer-file CDs and a GRUB boot image. Everything already in the ISO stays byte for byte the same, including both file systems and the UEFI boot entry, so UEFI PCs still boot Windows natively from the same disc.

3. Write it to a DVD or USB stick

# USB stick (replace sdX with the stick; everything on it is erased)
sudo dd if=Win11_w32eleven.iso of=/dev/sdX bs=4M status=progress conv=fsync

For a DVD, burn the ISO with any burning program. The image is hybrid, so the same file works for both.

4. Boot the 32-bit PC from it

Choose an entry in the boot menu (below). The first screen of Windows Setup takes several minutes to appear: the screen stays black or shows the Windows logo for a long time before that, which is normal.

Setup's TPM, Secure Boot, RAM, CPU and storage checks are bypassed with Microsoft's documented LabConfig registry keys, from an autounattend.xml on a small virtual CD that only the emulated PC sees.

Automatic install

This erases the first hard disk without asking. Everything on it is lost.

Instead of Setup's graphical installer, the automatic entry runs a script inside Windows' installer environment (WinPE):

  1. diskpart erases disk 0 and creates one NTFS partition
  2. dism applies the Windows 11 Pro image (the longest step)
  3. the slim settings are written into the new installation
  4. bcdboot installs the boot files
  5. an answer file for the first start is copied in, and the PC restarts

Windows then sets up its devices, restarts again, creates a local account called User without a password, and logs in automatically. There are no screens to click through: no Microsoft account, no network, no privacy questions. Expect several hours in total at the emulator's speed.

Slim settings

By default the automatic install switches off the background work that makes Windows 11 crawl on a slow machine. They are written into the installed system before its first start, so Windows never runs them at all.

AreaSwitched off
ServicesSysMain (prefetching), Windows Search indexing, telemetry (DiagTrack, dmwappushservice), Maps, Microsoft Defender (antivirus, network inspection, boot driver)
Visual effects"Adjust for best performance": no animations, transparency, peek or shadows; windows are drawn as outlines while dragging
Background activityBackground apps, widgets, suggested and silently installed apps, Edge staying open in the background
UpdatesAutomatic Store app and Edge updates (Windows Update stays on)
PowerHibernation and fast startup; the display and sleep timeouts
Scheduled jobsDefrag, telemetry collection, Defender's scheduled scan, WinSAT
With Defender off the installed system has no antivirus. That suits old offline machines and testing. Patch with --no-slim to keep Windows' defaults.

On an already installed system, most of these settings can be applied from an administrator command prompt. Windows refuses changes to Defender while it is running (Tamper Protection and the service keys' access lists), so Defender can only be switched off this way at install time or with the disk mounted elsewhere.

Booting without the DVD

After Windows is installed, boot the DVD once more and choose Install the W32Eleven boot loader on the hard disk. This writes GRUB, the emulator and its firmware into the unused area between the disk's partition table and its first partition (sectors 1–2046). From then on the PC starts Windows through the emulator directly from the disk.

Windows never notices: when it reads that area, the emulator shows it the original contents. Partitions must start at sector 2048 or later, which is what Windows creates.

Trying it in QEMU

QEMU's qemu-system-i386 with KVM behaves like a 32-bit PC and is the quickest way to try W32Eleven:

truncate -s 64G disk.img
qemu-system-i386 -enable-kvm -cpu host -m 3G \
  -cdrom Win11_w32eleven.iso \
  -drive file=disk.img,format=raw,if=ide,index=0

To test booting from a USB stick instead, replace the -cdrom line with:

  -device usb-ehci,id=ehci \
  -drive id=stick,file=Win11_w32eleven.iso,if=none,format=raw,readonly=on \
  -device usb-storage,bus=ehci.0,drive=stick,bootindex=0

More than 3 GB of RAM brings nothing: a 32-bit PC only sees the RAM below its PCI address range.

What the patch changes

  • The payload (emulator, firmware, answer files, disk boot loader and two GRUB images) is appended after the end of the ISO.
  • The El Torito boot catalog's BIOS entry points at the appended GRUB image. The original entry is saved, and the emulated PC still sees and boots it.
  • The ISO's unused first sector gets a boot sector and a partition entry (a hybrid MBR), so the same file boots from a USB stick.

Real hardware

  • Disks: the emulator has its own polled drivers for IDE / legacy-mode SATA and AHCI. Anything else the BIOS can boot from (USB sticks, SATA in other modes, NVMe with CSM) is read through the PC's own BIOS, by switching back to 16-bit real mode for each INT 13h call.
  • Display: the VESA graphics mode GRUB sets up (1024×768 preferred).
  • Keyboard and mouse: PS/2. USB keyboards and mice work through the BIOS's legacy USB emulation.
  • Network, sound and USB devices are not passed through to Windows yet.
W32Eleven hasn't been tested on real hardware yet. BIOSes differ more than QEMU's SeaBIOS, especially in their USB support. If you try it, please report what happened on GitHub.

Performance

Measured in the development harness (build/hosted32, a 32-bit Linux process) on one performance core of an Intel i9-12900KF, booting an installed Windows 11 (the first 60 billion guest instructions, from power-on to the desktop and services):

~525 MIPSaverage over the whole 60-billion-instruction boot
~1500 MIPSbest 5-billion-instruction stretch
~2100 MIPSpeak (0.5-billion-instruction window)
~45 MIPSinterpreter only, without the JIT

That's roughly 1/100 of native speed on a modern PC. A real 32-bit CPU is another 5–10× slower: Windows works, but slowly, and installing takes many hours. Fresh installations are at their slowest during the first hour, while Windows does its one-time background work; the slim settings avoid most of it.

How it works

  • Interpreter (src/emu/cpu.c, sse.c, x87.c): real, protected, compatibility and long mode; legacy, PAE and 4-level paging with a software TLB; lazy flags; x87, MMX, and SSE through SSE4.2. SSE floating point matches the hardware bit for bit in the fuzzer.
  • JIT (src/emu/jit64.c): translates x86-64 into i386 code. Superblocks across conditional branches, inline TLB lookups, a stack-region check per block, lazy flags with dead-flag elimination, block chaining, per-site indirect dispatch, separate hot and cold code. Whatever it doesn't translate runs in the interpreter, and execution is step for step identical to the interpreter.
  • The emulated PC (src/emu/): i440FX/PIIX chipset, PIC, PIT, CMOS clock, UART, PS/2, IDE with ATAPI and bus-master DMA, local APICs and IOAPIC with two CPUs, generated ACPI tables, Bochs VBE graphics, fw_cfg for SeaBIOS.
  • The bare-metal host (src/host/): Multiboot kernel, ATA/ATAPI and AHCI drivers, BIOS disk access through a real-mode thunk, VBE display, PS/2 passthrough.
  • Deterministic time: the emulated clock is driven by the instruction count, so every run is reproducible, which makes bugs reproducible too.

Troubleshooting

The screen stays black for minutes

Normal, especially before Setup's first screen and during the first start after installing. Also, unless the slim settings were applied, Windows turns the display off after a while: move the mouse.

Setup says the PC doesn't meet the requirements

Boot an entry from the patched disc, which attaches the answer file with the LabConfig bypasses, and keep cpus=2. Setup refuses PCs with fewer than two cores.

"Why did my PC restart?"

Windows shows this page after its first-start setup (OOBE) has failed several times. Choose Next to make it try again. If it keeps coming back, it's most likely an emulator bug: please report it with the crash reports from C:\ProgramData\Microsoft\Windows\WER\ReportQueue.

"No ATAPI CD/DVD drive with an ISO 9660 disc found"

The emulator couldn't find the boot medium. For USB sticks and unusual controllers it falls back to the BIOS automatically. Add cdrom=bios to force that path.

Everything is very slow

Expected: see Performance. Give a fresh installation its first hour, use the automatic install's slim settings, and use the fastest 32-bit CPU you have.

Development

build/hosted and build/hosted32 run the same emulator as a Linux process:

build/hosted32 --ram 2048 --bios /usr/share/qemu/bios.bin \
  --vgabios /usr/share/qemu/vgabios-stdvga.bin --hda win11.img --snapshot \
  --insns 60000000000 --hash

Its options include --iso, --cdrom, --hda, --snapshot (writes go to a temporary overlay), --insns N, --hash and --hash-every N (guest state hashes for comparing runs), --shot, --no-jit, and --ctl FIFO (drive a running guest: press tab enter, type hello, mouse 10 -5 1, shot out.png, stop).

Tests

make jit-check       # interpreter vs JIT: identical guest state
make cpufuzz         # random instructions: host CPU vs emulator
make boot-test       # KleinOS ISO on the bare-metal image (KVM)
make boot-test-486   # the same on QEMU's software 486

Every JIT change is checked by running Windows with --hash-every 1000000000 for 60 billion instructions and comparing all 60 checkpoints (RAM, framebuffer and registers) against an interpreter-only run.
